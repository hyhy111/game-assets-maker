# Design

## Context

步骤 1 当前无条件渲染模型状态卡，并在挂载时为步骤 2 调用模型预加载。步骤 2 已有独立的模型状态读取、预加载、模型变更监听和处理前就绪检查，因此它是唯一需要向用户呈现下载状态的步骤。模型状态卡的下载来源目前使用原生 `select`，与项目其他采用共享选择控件的界面不一致。

## Goals / Non-Goals

**Goals:**

- 让 U2Net 的显式下载、进度和失败重试只在背景移除步骤出现。
- 不改变用户触发下载、模型状态 API、持久化模型位置或步骤 2 的就绪门槛。
- 让模型已就绪时不占用步骤 2 的设置区域。

**Non-Goals:**

- 不替换 U2Net、增加其他模型或改变下载来源。
- 不自动下载模型，也不在步骤 1 后台下载模型。
- 不改变帧提取或背景移除的处理参数和结果。

## Decisions

### 1. 移除步骤 1 的模型状态消费者

步骤 1 删除模型状态卡、模型状态 store 引用以及仅为步骤 2 而触发的预加载调用。这样缺失模型、下载进度和失败状态不会泄漏到帧提取 UI，也不会在用户尚未到达背景移除时产生模型准备请求。

### 2. 以步骤 2 的状态决定卡片可见性

步骤 2 保留现有挂载和模型变更时的状态检查。模型状态卡只在 `needs_download`、`downloading`、`initializing` 或 `failed` 状态显示；`ready` 状态直接隐藏，处理按钮继续使用既有的就绪判定。

### 3. 下载来源复用共享选择控件

模型状态卡复用项目现有的共享非原生选择控件呈现下载来源。该控件仅承载字符串值 `modelscope` 与 `github`，初始值保持 `modelscope`；选择变更继续写入现有来源状态，因此下载和失败后的重试都会使用用户当前选择。复用组件可继承一致的尺寸、视觉样式和键盘交互，不新增依赖，也不改变 store 或后端 API 的参数契约。

### 4. 保留现有下载交互

模型状态卡继续负责用户选择 ModelScope 或 GitHub、显式重试和进度显示。无需修改前端 store 或后端 API；页面只在正确步骤订阅它们。

## Risks / Trade-offs

- [从步骤 1 进入步骤 2 时模型检查稍晚] → 步骤 2 挂载时立即读取并准备模型，下载仍由用户显式启动。
- [ready 状态卡隐藏后缺少正向提示] → 步骤 2 的启用处理按钮已表达可用状态，避免重复占用空间。
- [改变共享状态卡导致下载流程回归] → 保持状态卡、store 与 API 完整不动，使用步骤可见性和下载来源传递测试覆盖。

## Migration Plan

1. 添加步骤 1 与步骤 2 的模型状态卡可见性测试，覆盖缺失、就绪、下载/初始化和失败状态。
2. 将模型状态卡的下载来源替换为共享选择控件，覆盖默认来源、键盘操作及下载/重试来源传递。
3. 移除步骤 1 的模型预加载和渲染，收紧步骤 2 的卡片可见条件。
4. 运行模型状态组件、编辑器视图和相关 TypeScript 检查，验证模型下载仍需要用户动作。
